INTRODUCTION                                    *omarchy-plugin-dev-introduction*

omarchy-plugin-dev.nvim detects schema-version-1 Omarchy shell plugin manifests
and provides explicit Overseer tasks, native LSP setup, project-local maps,
and a small dashboard. It stays inactive for unrelated QML projects and never
runs a project command merely because a buffer opened.

==============================================================================
REQUIREMENTS                                    *omarchy-plugin-dev-requirements*

- Neovim 0.11 or newer
- stevearc/overseer.nvim
- omarchy and Qt 6 qmllint for Check
- omarchy-shell for refreshing prepared installations
- journalctl for shell logs
- jq and rsync for validation; util-linux (flock and findmnt) for safety checks
- git for clones; curl for GitHub releases; GNU coreutils and findutils
- Qt qmlls for LSP features

On Arch: >bash
  sudo pacman -S qt6-declarative
<
The plugin also recognizes the Mason qmlls package.

INITIALIZATION                                *omarchy-plugin-dev-initialization*

                                                               *:OmaDevInit*
:OmaDevInit
    Validate the detected project with the installed Omarchy validator and
    add the hidden task directory to .gitignore before creating:
        .omarchy-plugin-dev/task-config.json

    Create Local project and Local link entries. If an executable
    ./scripts/test or ./tests/all.sh exists, choose whether to configure it
    for these entries. Otherwise their tasks objects are empty. Initialization
    never installs a plugin or executes a discovered runner.

:OmaDevInit!
    Explicitly approve replacing the existing task configuration. Without !,
    an existing file is preserved and an overwrite choice is shown.
    Replacement creates new entries, not a merge of previous custom tasks.

Configure and select a target before running tasks. Version 2 is the only
accepted task format. There is no secondary sources file, project-local Lua,
old-schema reader, or automatic migration. See |omarchy-plugin-dev-sources|.

Each build entry has its own tasks object. Each task has a non-empty command
argv array and optional description. Shell command strings are invalid in
JSON. The test task supplies Test and the full build; false disables it.
The names check, hot_reload, logs, and build are reserved in JSON. Other names
appear in the task picker (press p). Relative commands run at the selected
destination, while configuration stays in the editor project.

==============================================================================
COMMANDS                                            *omarchy-plugin-dev-commands*

                                                                   *:OmaDev*
:OmaDev
    Open the project dashboard. Build opens first and contains Actions; Status
    shows project and tool information; Settings contains the build keybindings.
    Tab / Shift-Tab cycle tabs; 1 / 2 / 3 select them directly. Press r to
    refresh all information and rerun official validation without changing
    tabs. Navigation alone does not rerun checks. Refresh reads saved project
    files and current plugin options; it does not source configuration files.
    If the source project can no longer be inspected, the dashboard closes
    with an explanation rather than displaying stale information.

                                                               *:OmaDevTest*
:OmaDevTest
    Run the selected entry's "test" argv. Missing or disabled tests produce
    an explanation rather than executing another entry's runner.

                                                          *:OmaDevHotReload*
:OmaDevHotReload
    Validate and lint the selected destination, then restart the Omarchy
    shell exactly once. No test, copy, clone, or relink step.

                                                            *:OmaDevBuild*
:OmaDevBuild
    Check the selected destination, run its configured test, then restart
    once. An explicit false disables tests with an informational message.
    Without a configured test, a Tests skipped step warns and continues:
    - Tests detected but not configured; skipping
    - Tests NOT detected; skipping
    Both warnings point to :OmaDevInit. Detection never executes a runner.
    In Git worktrees, test-directory detection considers existing tracked and
    nonignored files, not ignored reference copies or deleted test sources.
    A failed test, invalid task configuration, or unavailable configured test
    executable still stops the default workflow. A complete tasks.build
    override owns its test policy.

    A skipped-test card keeps SUCCESS so the build can continue, but adds a
    "⚠ WARN: TESTS SKIPPED" heading in DiagnosticWarn and the dedicated warning
    message. The setup hint remains in the output. The plugin wraps the
    existing Overseer renderer for these warnings and the parent task's
    build-target identity; unrelated cards are unchanged. A warning notification
    replaces the skipped step's usual success notification. Set notify=false
    to suppress the plugin
    notification; the card warning remains visible.

                                                             *:OmaDevHealth*
:OmaDevHealth
    Run the standard `checkhealth omarchy-plugin-dev` report.

==============================================================================
MAPPINGS                                            *omarchy-plugin-dev-mappings*

Defaults exist only in QML and qmljs buffers inside detected Omarchy projects:

  <C-b>            Check selected target and restart once
  <C-S-b>          Check, test selected target, and restart once
  <localleader>t   Test
  <localleader>o   Dashboard

Test and dashboard mappings preserve existing mappings at their configured
keys. Build mappings take precedence. The plugin does not change
maplocalleader. Every mapping is normal-mode, buffer-local, and has a
human-readable description.

CONFIGURATION                                  *omarchy-plugin-dev-configuration*

Call setup through a plugin manager's opts or directly. These are the defaults:
>lua
  require("omarchy-plugin-dev").setup({
    diagnostics = {
      virtual_text = false,
    },
    format_on_save = true,
    mappings = {
      enabled = true,
      hot_reload = "<C-b>",
      build = "<C-S-b>",
      test = "<localleader>t",
      menu = "<localleader>o",
    },
    executables = {
      journalctl = "journalctl",
      jq = "jq",
      omarchy = "omarchy",
      qmllint = "auto",
      qml_language_server = "auto",
      rsync = "rsync",
    },
    logs = {
      follow = true,
      match = "_COMM=quickshell",
    },
    notify = true,
    log_level = vim.log.levels.INFO,
    qml_import_paths = { "/usr/share/omarchy/shell" },
    task_layout = { height = 1 / 3, list_width = 1 / 2 },
    tasks = {},
  })
<
Detected plugin QML uses four-space indentation and is formatted by qmlls
before each save. This follows Qt's official QML Coding Conventions and the
four-space qmlformat default:
https://doc.qt.io/qt-6/qml-codingconventions.html
https://doc.qt.io/qt-6/qtqml-tooling-qmlformat.html
Set format_on_save=false to opt out.

QML JavaScript (qmljs) keeps language support and diagnostics, but the plugin
does not format it on save: qmlls may never answer its formatting requests. It
sets b:autoformat=false for editor hooks that honor that convention, even with
format_on_save=false. Their indentation is unchanged; leaving plugin ownership
restores the previous b:autoformat value.

Set mappings to false, mappings.enabled to false, or an individual mapping to
false to disable defaults. Executable names, QML import paths, notifications,
and Overseer task definitions are configurable. Setup and commands remain
available without mappings.

The default initial bottom-panel layout is: >lua
  task_layout = { height = 1 / 3, list_width = 1 / 2 }
<
height is a fraction of available editor height; list_width is the task list's
share of the two panes' content width. Both must be greater than 0 and less
than 1; decimals such as 0.15 are accepted. Sizes round to the nearest whole
row or column and are clamped to fit the editor and keep both panes usable.
An empty table uses the fractions above; false preserves Overseer's layout.

The layout applies only when a plugin action opens a closed panel. Existing
panels and manual resizing are left alone; closing and reopening reapplies the
initial sizes. Overseer's global settings and panels opened directly through
Overseer are unchanged.

In the dashboard, c or Enter on Plugin settings opens configuration help.
Set config_file to open your Lua settings file instead: >lua
  opts = {
    config_file = "lua/plugins/omarchy-plugin-dev.lua",
  }
<
Use your actual filename. Relative paths use stdpath("config"), including
custom Neovim config locations; absolute paths are also accepted. The file
must already exist. Opening it does not execute it or change any settings.
Restart Neovim after changing mappings.

For a repository containing more than one QML target, qml_file_filter may be
a function that decides whether a file belongs to the detected Omarchy plugin.
It receives a table containing path, relative_path, root, and a copy of the
validated manifest. It must return a boolean. Returning false leaves that
file's LSP, formatting, mappings, and built-in linting untouched. Without the
callback, ordinary descendants of the plugin root retain the default behavior.
The plugin does not infer foreign project markers or target layouts.

In a Git working tree, built-in lint includes tracked and new nonignored QML
sources but not ignored artifacts. Non-Git projects use recursive discovery.

The qmllint value "auto" prefers /usr/lib/qt6/bin/qmllint and accepts a PATH
candidate only when it reports Qt 6 or newer. An explicit override is honored
as-is. The dashboard shows the selected path and version.

Each executables entry accepts a command name or path. qml_language_server
and qmllint also accept "auto". Set qml_import_paths to an array of QML import
directories; its default contains /usr/share/omarchy/shell. A configured array
replaces that default, so include the shell directory if it is still needed.
The plugin adds discovered Qt imports and an Omarchy import bridge separately.

The QML language server prefers the system Qt qmlls, then PATH and Mason. A
generic qmlls attached by another Neovim integration is detached only from
detected Omarchy Plugin buffers. After attachment settles, a detached client
is stopped only when it owns no other buffers. If graceful shutdown leaves its
process alive, the process is terminated after a short grace period. The
project-aware server resolves qs.* imports through a generated cache bridge
and discovers Qt's QML module path from its Qt 6 tools. The bridge supplies
tooling types for grouped Style and Color properties and the documented
PluginBarApi type used by Panel.bar without changing the installed shell.
Automatic CMake discovery is disabled because ordinary Omarchy plugins have
no CMake build.
The plugin does not write .qmlls.ini or other tooling files into the project.

Inline diagnostic text is disabled for this server by default because qmlls
cannot fully model every runtime-injected Omarchy object. Underlines, signs,
diagnostic pickers, and the Overseer lint quickfix list remain available. Set
diagnostics.virtual_text=true to restore it, or diagnostics=false to inherit
Neovim's global diagnostic display.

TASK OVERRIDES                                  *omarchy-plugin-dev-task-overrides*

The setup option tasks contains Overseer task specifications, separate from
the project JSON format. Built-in override names are check, hot_reload, build,
and logs. Tests belong in each JSON build entry, not in a global Lua override.
Restart is an internal step; change its parent workflow to customize it.

A table shallowly replaces fields of a built-in specification; nested fields
such as strategy and components are replaced as a whole. A function receives
{ root, default, project }, where default is a copy of the built-in spec and
project is the plugin's project module. root is the resolved destination.
Return the task specification to run.

For example, rename the check task while retaining its validation and lint
steps: >lua
  require("omarchy-plugin-dev").setup({
    tasks = {
      check = function(context)
        context.default.name = "Validate and lint plugin"
        return context.default
      end,
    },
  })
<
A build table with cmd or strategy replaces the complete workflow. A
build function may also provide a workflow without a configured test.
These overrides own their check, test, and restart policy.
A partial build table, such as a name change, retains the default test policy:
run configured tests, otherwise warn and skip.

Additional task names appear in the dashboard's picker. Their setup values
may be full Overseer specs or functions receiving { root, project }. A
project JSON task with the same custom name takes precedence over setup.

Returned specs run at the selected destination and receive project metadata.
Relative cmd executables containing a slash resolve from that directory.
Custom strategies remain responsible for any tasks they create themselves.

SOURCES                                             *omarchy-plugin-dev-sources*

Build's Sources section lists the ordered builds in task-config.json. Names
must be unique but are otherwise yours; there is no fixed number of entries.
The shipped examples/task-config.json shows Local project, Local link, Upstream,
and Pinned variants using keyboard-layout. Adapt its paths and repository.

A minimal entry with an explicitly configured test looks like this: >json
  {
    "version": 2,
    "builds": [
      {
        "name": "Local link",
        "description": "Point Omarchy at this checkout without copying it",
        "type": "symlink",
        "source": ".",
        "destination": "~/.config/omarchy/plugins/io.example.plugin",
        "tasks": {
          "test": { "command": ["./scripts/test"] }
        }
      }
    ]
  }
<
Use your manifest's id in the destination. Do not configure an example test
command unless that destination actually supplies it. Omit test to warn and
skip; use "test": false to explicitly disable it. Empty tasks objects are valid.
JSON has no comments or trailing commas; use description for explanations.

Types:
- local-source: source and destination must resolve to the same existing folder.
  It is never copied, created, or deleted.
- symlink: source is an existing folder. Create the link at destination once.
- git-clone: source is a repository URL. Clone at destination once.

Filesystem paths resolve from the editor project's root, not the JSON directory
or Neovim's current working directory. Absolute and ~/ paths also work.
Only git-clone accepts ref, with exactly one selector:
- "tag": "v1.2.3": an exact tag
- "commit": "<full object id>": 40 or 64 hexadecimal characters
- "release": "v1.2.3": a public GitHub release tag, requiring a GitHub HTTPS URL
Without ref, clone the default branch. Releases select source, not assets.
No downloaded build, install, or task configuration is automatically executed.
Prepared files must pass Omarchy validation and match the project's plugin id.

Selection prepares a missing destination or reuses a matching one. It does not
fetch, pull, or reset existing checkouts. Selecting the active row changes no
files and does not reload the shell. If a later build finds a missing or
conflicting destination, select the entry again; builds never prepare it.
Saved path and command changes are read on refresh, selection, and build.
A changed path must already be ready before Build can use it.

Enter opens the existing aligned confirmation popup. y/Y confirms; n/N,
q, or Escape cancels. j/k, arrows, Tab, and Enter also work. Values wrap in full.
Ready destinations use normal values and green status; other destinations use
dim values and yellow status. Colors come from the theme. Destructive choices
default to red [N]o; other choices default to green [Y]es.

Replacement applies only to the occupied destination being changed:
- Unlink a symlink without deleting its target; report that operation.
- Ask before deleting any Git checkout, even if clean. Show actual modified,
  untracked, and ignored file counts, plus available local commit comparisons.
  Remote-tracking information can be stale; it does not prove publication.
- Never delete the editor project, configured local sources, or their parents.
- Refuse ordinary non-Git folders and Git worktrees with history stored
  elsewhere. Move or remove those explicitly yourself.
There are no automatic backups. Prepare the replacement first; after approved
permanent deletion there is no rollback guarantee if the final move fails.

Only the selected name is remembered under stdpath("state") in
omarchy-plugin-dev/selections/. Paths and commands always come from the current
project configuration; a remembered name never grants permission to delete.
Only one row gets a star, and only when that selected folder is installed.
A star does not prove QML runtime health or that files remain unedited.

Omarchy's installed path is ~/.config/omarchy/plugins/<id>, independently of
XDG_CONFIG_HOME. Do not put duplicate copies of an id in its scanned directory.
Preparing that path requests a plugin rescan but preserves shell.json and enabled
state. Enable a new plugin yourself with omarchy plugin enable <id> if needed.
A rescan affects shell plugins broadly, not just the chosen plugin.

Git clones retain .git, including tagged clones. Omarchy's own updater can
advance them and can follow symlinks into development checkouts. These targets
are not protected from omarchy plugin update. Only use sources you trust.

==============================================================================
BUILD SEMANTICS                                        *omarchy-plugin-dev-build*

There is no compile step for ordinary Omarchy QML plugins. Both build mappings
use an Overseer orchestrator and expose omarchy restart shell as their final
step. This prevents QML components and IPC handlers from surviving from the
previous plugin generation.

Build runs at the selected destination, not implicitly in the editor project.
Tests, relative commands, and file discovery use that same directory. The
editor project's configuration supplies commands; no downloaded task file is
loaded. Build-and-restart refuses a destination that Omarchy does not use.

Validation retains its temporary staged copy and existing file filters. In Git,
tracked and nonignored untracked files are included; deleted files are omitted.
Outside Git, staging applies .gitignore filters and excludes .git/,
.omarchy-plugin-dev/, .sublime/, .luacov, and coverage/. This validates files;
it does not deploy a copy. The obsolete copy-deployment helper was removed.

The parent Overseer card shows INFO: BUILD TARGET with name, type, destination,
resolved directory, and actual revision/dirty state. The heading uses
DiagnosticInfo, labels are dim, and values use the normal foreground. These
values are captured when the task is created and remain on historical cards.
An old task cannot be replayed against changed configuration or another target;
start a fresh task through OmaDev to resolve the current selection.

A per-plugin lock covers the whole operation. Child commands retain a shared
lease until they actually exit, including after cancellation, so a source switch
cannot delete a checkout while a stopped task is still shutting down. Built-in
steps recheck destination identity before running. Custom strategies own any
additional processes they launch.

==============================================================================
TROUBLESHOOTING                              *omarchy-plugin-dev-troubleshooting*

Run :OmaDevHealth, or invoke the native command directly: >vim
  :checkhealth omarchy-plugin-dev
<
The report checks the Neovim version, Overseer, exact executable paths, the
Qt 6 qmllint version, and the QML language server.

For runtime output, open :OmaDev, press p, and choose Shell logs. This uses
journalctl for the current user's current boot, following Quickshell logs by
default. Configure logs.follow and logs.match to change that behavior.
